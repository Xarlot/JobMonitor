# Job Monitor v2.1.0

The auto-rerun engine stops being a black box.

It always worked out a precise reason for every run it passed over — and then threw it away. So a pull
request that had quietly stopped being retried looked exactly like one with nothing to do, and the only
way to tell them apart was to reason about the policy from the outside. Every decision is now recorded,
including the decisions *not* to act, and readable inside the app.

Three real bugs were hiding behind that silence. All three are fixed here, and each one was found by
reading the log that now exists.

Pull requests also gain a **merge** button: it clears the description and hands the PR to GitHub to merge
once its checks pass.

## The Diagnostics tab

Desktop, opt-in under **Settings → Diagnostics**. It reads Job Monitor's own log inside the app — the
tail of the file, newest first, following live, because the run worth reading is always the one that just
happened.

- **Search covers the attached details**, not just the message. A run id, a PR number or a failure
  fingerprint finds its own records even when the sentence never mentions them.
- **Filter by scope** — `auto-rerun`, `api`, `claude`, `log-cache` — built from what is actually in the
  file rather than a hard-coded list, so a new scope can't be quietly missing.
- **Every line expands** into the facts behind it.
- It reads a **bounded tail** (512 KB of a possible 5 MB by default) and says so — *the last 512 KB of
  4.1 MB* — instead of implying it has everything. A line that won't parse is shown rather than dropped:
  one is usually a crash mid-write, and knowing it is there beats a silent gap.

Off by default. It is a window on the app rather than on the work.

## What the log now says

Every auto-rerun decision, with the facts needed to act on it rather than just a verdict:

| Verdict | What comes with it |
|---|---|
| too old | the age of the last attempt against the configured window |
| the failure repeated identically | the fingerprint, the streak, and the allowance |
| already re-run | the record that settled it, and how many re-runs were actually made |
| could not be checked | what went wrong when computing the fingerprint |

The engine's own state is logged whenever it changes, because `off`, `no-permission` and `no-workflows`
stop the poll entirely — a tick-side log would go quiet exactly when someone is asking why nothing
happened. A verdict is written when it **changes**, not on every poll, so a size-capped file cannot fill
up with one repeated sentence.

Auto-rerun activity also shows **on the pull request** now, as a `re-run ×3` badge whose hint lists every
attempt — and, if the engine has since gone idle, why. It used to be one shared list at the top of the
Failures tab, which put it in the wrong place twice over: you had to be on that tab, and once more than
one PR was being retried the list said nothing about which.

## Arm auto-merge

![Pull requests](../screenshots/pull-requests.png)

Every open pull request gets a **merge** button that does two things: **deletes the description**, then
**arms auto-merge**. It confirms first and shows you the description it is about to delete, because that
text cannot be recovered — a pull request body has no edit history for this app or the API to restore
from.

Clearing happens *before* arming, deliberately. Auto-merge is not "merge later": a PR whose checks are
already green merges within seconds of being armed, so clearing afterwards would race the merge and lose —
failing precisely in the case the feature exists for. The cost of that order is stated rather than
hidden: if arming then fails, the dialog tells you the description is already gone instead of implying
nothing happened.

Pick the strategy — squash (the default), merge commit or rebase — under **Settings → PR automation**. It
must be one the repository allows, or GitHub refuses and says so in the dialog.

A PR that already has auto-merge shows an `auto-merge` badge instead of the button, naming the strategy
and who armed it. That badge is also how you tell at a glance which PRs the auto-rerun engine will act on
at all — something the list previously gave no way to see.

## The three bugs

**A pull request being actively retried would silently stop being retried.** The "ignore runs older than"
window was measured from the run's `created_at`, which GitHub never moves. A run that had been re-run for
three days still reported itself as three days old, fell out of the 72-hour window, and went quiet — while
its most recent attempt was minutes old. It is now measured from `run_started_at`, which resets with each
attempt. GitHub's own refusal to re-run anything more than 30 days after its first run is enforced
separately, from `created_at`, because that is the clock GitHub uses. Conflating the two is what caused
this.

**The engine reported "this attempt was already re-run" about attempts it had never re-run.** A decision
*not* to re-run was filed among the re-run requests, so the number of re-runs could not be read from the
app's own record — it was overstated by one — and the real reason was hidden behind a false one. Requests
and declined verdicts are now separate things, the stored verdict is reported as itself, and existing
records are migrated on read so nothing has to be cleared.

**The identical-failure limit lapsed whenever a failure could not be fingerprinted.** An uncomputable
fingerprint was treated as permission to proceed — so an intermittently failing lookup suspended the limit
exactly while something was already wrong, and a run climbed toward the attempt ceiling on a failure
nobody had ever compared. It was caught doing this. Now, if it cannot check, it does not re-run: it says
why, on the PR badge and in the log, and tries again on the next poll.

## Identical failures are a count now

**Allow the same failure this many times — 5 by default**, replacing the *stop when the failure repeats
identically* switch. That switch was this same rule with the count fixed at 2, which gave a flaky test
that fails identically twice and passes on the third go no chance at all.

The count is a **consecutive** streak, so a different failure in between starts it over, and it spans both
the re-runs made and the verdict the engine stopped on — otherwise re-running by hand would reset it and
the allowance would never actually run out. `0` switches the brake off entirely.

A verdict cached under a tighter limit is **reconsidered** when the limit is raised. A stopped run's
attempt number never changes again, so it would otherwise stand forever and make the new setting look
inert.

## Upgrading

No migration needed, and nothing has to be cleared — old auto-rerun records are upgraded as they are read.
Two things to know:

- **`stopOnIdenticalFailure` is gone**, replaced by `maxIdenticalFailures`. A saved config carrying the old
  key takes the new default of **5**. If you had the brake switched *off*, that is a tightening rather than
  a loosening: set *Allow the same failure this many times* to `0` under **Settings → PR automation** to
  get the old behaviour back.
- **Arming auto-merge needs the same token as re-running jobs** — a classic token with the `repo` scope on
  a repository you can write to. Without one the button stays hidden, as the re-run controls do.
