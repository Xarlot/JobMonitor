# Job Monitor v1.2.0

Failures stop being something you go looking for. They get collected into one live list, written up as
a bug report you can paste straight into Teams or a GitHub issue, and — for pull requests waiting on
auto-merge — retried without you. On the desktop, your own `claude` will read a failure and tell you
what broke, why, and who broke it.

![Failures](../screenshots/failures.png)

## The Failures tab

Every failing job across your open pull requests, the recently merged ones, and the latest run of every
flow you track — in one list that refreshes on the normal polling cycle, with a count on the tab. Split
into **Pull requests** and **Flows**, a group per PR or flow, everything collapsed by default so a red
board reads as a short list of what is broken. It looks back one week and no further.

Each failure comes with a **Markdown bug report**: the PR and branch, the workflow and run, the step
that failed, the failing tests with `file:line`, and a tail of that step's log. The **GitHub / Teams**
switch changes how it reaches the clipboard — GitHub gets Markdown, Teams gets rich text, because Teams
does not render Markdown pasted from the clipboard.

## Reading the log

![The log, coloured](../screenshots/failures-log.png)

Three views: the **job's own log**, the **whole run's failed steps** via `gh` — the only view that shows
an upstream job's output when the failure you clicked is an aggregator — and **Claude's rewrite**, with
the decisive lines first and the noise cut. The first two are coloured locally, so it is instant and
costs nothing.

## Explain with Claude (desktop only)

Four analyses, each on the model its job needs:

| | Answers | Model |
|---|---|---|
| **Quick read** | what failed | Sonnet, medium |
| **Deep analysis** | why it failed | Opus, high |
| **Readable log** | the log, rewritten | Sonnet, low |
| **Who broke it** | which commit, and whose | Opus, medium |

![Who broke it](../screenshots/who-broke-it.png)

**Who broke it** rules out a flaky test and then infrastructure *before* naming anyone: on a
merge-gated branch the code has already passed the workflow that is now failing, so both are likelier
than a bad commit. When several commits landed between runs it weighs them by what each one changed and
gives each a likelihood with the evidence behind it — and under 40% it says it does not know rather
than promoting the least-bad guess to an accusation.

The procedures are **Claude Code skills** (`.claude/skills/`), so you can run the same triage by hand in
an ordinary `claude` session.

Analyses are kept for a week, per failure and per task. An unfinished run can be **continued** rather
than restarted.

## Auto-rerun

For a pull request with **auto-merge enabled**, when a run of a workflow you have named finishes as
failed or timed out, Job Monitor asks GitHub to re-run its failed jobs. Two brakes: **max attempts**
(10 by default) and **stop when the failure repeats identically**. Cancelled runs are never re-run.

## Settings and diagnostics

![Settings — AI integration](../screenshots/settings-ai.png)

**Check AI integration** reports whether `claude` and `gh` are installed and signed in. The desktop app
also keeps a diagnostics log — one JSON object per line — recording every analysis, the commands it ran
and how each ended. It holds sizes and outcomes, never your token and never the contents of a CI log.

## Upgrading

No migration needed; new settings fill in with defaults. To use the AI features you need the desktop
app and the [`claude`](https://docs.claude.com/en/docs/claude-code/overview) CLI;
[`gh`](https://cli.github.com/) is optional but makes the analyses wider. Re-running failed jobs needs a
**classic token with the `repo` scope** on a repository you can write to — without one, those controls
stay hidden.
