# Job Monitor v2.2.0

Long-lived feature branches get a tab of their own — and it answers the question a pull request list
never does: *why is this sitting there?*

Work on a branch shared between your fork and the upstream was invisible to this app. Both ends of its
pull requests live in the upstream, and the PR tab filters on the fork being the head — so those pull
requests were excluded outright. Nothing here could see them, which also meant nothing here re-ran their
failed jobs.

The new tab tracks those branches, shows how far each merge has actually got, and does the three things
the routine around such a branch consists of.

## Feature branches

Opt-in, under **Settings → PR automation**. Off by default: most repositories have no such branches, and
nothing is polled or written while it is off.

A feature branch is one under a prefix — `feature/` by default — that exists in **both** your fork and
the upstream. A branch only one of them has is not shared work, and does not appear: you cannot pull a
branch into a fork that hasn't got it, and a branch only you have is not something to ship.

Branches are found through GitHub's prefix-matching refs endpoint rather than by listing every branch and
filtering here. On a repository with several hundred branches that is the difference between two requests
and sixteen, each carrying a full commit object it would then throw away.

## Where the merge has stopped

This is the part worth having. A pull request that is merely "open" tells you nothing. One that is open,
green, mergeable and **unarmed** tells you it is waiting for a person; one that is open, green and armed
tells you to stop looking at it.

So each pull request gets a stage strip:

> **Pull request opened** `#38100` · **Checks** *1 of 2 passed* · **Mergeable** *waiting on required
> checks or a review* · **Auto-merge armed** *squash when checks pass* · **Merged**

The reason it is stuck is spelled out rather than left to be inferred — *behind the base branch*,
*conflicts — this one needs a working copy*, *some checks failed, but none of them are required*. That
comes from `mergeable_state`, which only the single-pull-request endpoint carries and which GitHub
computes **asynchronously**: it answers `null` until a background job finishes. So it is polled until it
means something rather than read once and believed. The set of values is undocumented and GitHub extends
it, so one this app doesn't recognise is reported as itself instead of being forced into a neighbour.

## The three actions

Each confirms first, and each reports **which of its steps ran** rather than a bare success or failure.
That matters because these are multi-step writes: "it didn't work" is not a useful thing to be told when
a pull request now exists.

### Sync from the default branch

Opens a pull request from the default branch into the feature branch, then either arms auto-merge or
merges it outright.

That fork in the road is not a preference. **GitHub only allows auto-merge on a pull request it cannot
merge right now** — arming a clean one is refused with *Pull request is in clean status* — and a
backmerge into an unprotected feature branch is clean from the moment it opens. Treating that as a
failure would mean the common case never worked. So mergeability is established first, and it picks the
call that will actually do the job.

Always a merge commit, never a squash. Squashing the default branch into a feature branch replaces
hundreds of commits the two repositories share with one that exists nowhere else, and every later merge
between them conflicts against history they no longer agree on.

### Ship into the default branch

The reverse direction, arming auto-merge with the strategy you configured.

This one **never merges on its own.** Where the backmerge above completes a mechanical operation you
asked for, this lands feature work in the branch everyone builds on. If GitHub reports the pull request
as already mergeable, nothing is queued and nothing is merged — you get a **Merge now** button and a
second, deliberate click.

### Pull into my fork

Updates your fork's copy of the branch from the upstream's, through GitHub's own fork-sync.

Each branch says where its two copies stand — *your fork is 3 commits behind*, *diverged — 4 commits
behind, 2 commits ahead*, *5 commits ahead, nothing to pull*. The direction matters more than the
difference: being behind fast-forwards harmlessly, while having commits of your own means GitHub
**merges rather than refusing**, leaving a merge commit in your fork that nothing here can undo. The
dialog tells you which of those you are about to do.

(An earlier draft of this tab just said "your fork is at a different commit", which described both
cases equally well and told you nothing about either.)

It is blocked outright unless your fork really is a fork of the repository you configured as upstream.
The endpoint has no way to name where to sync *from* — GitHub uses the fork's actual parent — so a
mismatch would succeed while pulling from an unrelated repository, with no error to notice. That is
checked before the action is offered, and the branch GitHub says it synced is checked after.

## Pull request text written for you

Desktop app. The shipping pull request's title and description are written by the `claude` CLI already on
your machine, from the branch's commit subjects and changed files.

The app fetches that material itself, so the task is a single turn with **no tools, no shell and no
network access** for the model — it is summarising text it was handed, not investigating anything. You
see the result in editable fields and can change any of it before a pull request exists.

Every way this can fail lands on a template instead: a browser, a missing CLI, the AI integration
switched off, a slow reply, a reply that ignored the output contract. The pull request is the product;
the prose is decoration, and decoration must not be able to stop it.

Issue references and @mentions are stripped from whatever comes back, regardless of the instruction not
to write them. A hallucinated `Fixes #123` **closes somebody's issue** the moment the pull request
merges — a consequence outside this app's power to undo, and not one to leave to a model's compliance.

Model and effort live under **Settings → AI integration**, alongside the four analysis tasks.

## Auto-rerun covers these too

The engine's rule has always been "auto-merge is armed", and these pull requests arm it. But the
dashboard cannot see them, so without this a single flaky check would park an armed pull request
indefinitely — exactly the failure the new tab exists to make visible.

They are now handed to the engine along with the dashboard's own. Every existing brake applies unchanged:
the workflow allowlist, the attempt ceiling, the identical-failure streak, the run-age window and the
rate-limit throttle.

## Also in this release

- **A fork repo name** under **Settings → Repository**, for the rare fork that was renamed. Blank still
  means "the same name as the upstream" — which is what every earlier version assumed outright, since it
  never needed to address the fork repository at all.
- **Write failures now say what was refused.** Every refusal message was phrased for re-running jobs,
  which was true when that was the only write this app made. *"This run is too old to re-run"* in answer
  to a failed pull request is not.
- **The security claim in `development.md` is accurate again.** "Everything is read-only except one
  opt-in feature" was already stale at 2.1.0 and this release makes it plainly wrong; it is now a table
  of every write the app can make and how each one is reached.
- **A test that had quietly expired.** `failures.test.ts` pins its fixtures to absolute dates and the
  code under test drops anything older than a week — so all 26 of its assertions passed until seven days
  after they were written and then failed permanently, saying nothing about the code either way. Its
  clock is now frozen to the date it was written against.
