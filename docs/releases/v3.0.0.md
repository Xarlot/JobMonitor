# Job Monitor v3.0.0

Nearly everything this app is built on moved a major version at once — React, Primer, TypeScript and
the table library. Nothing about what the app *does* has changed, which is the point: this is the
release that pays off upgrades that had been accumulating, so that the next feature is written against
current parts rather than around old ones.

Electron was the exception, and not by choice: 43 was upgraded to and reverted, because it breaks the
tray. That is the one thing here worth reading before you install — the details are under *Under the
hood*.

It is a major version because the user interface was rewritten to get there, not because the product
was redesigned. Almost everything looks and behaves as it did. The handful of places where it does
not are listed below, and one of them is a real fix.

Two features arrive with it: **a tab for long-lived feature branches**, and **an auto-rerun engine
that says what it decided** instead of working it out and throwing it away.

## Why it had to be one release

These upgrades are not independent. Primer 36 requires React 18 exactly, so React 19 is unreachable
without Primer 38 — and Primer 38 removes the `sx` prop, the `Box` component and the `Octicon`
component outright. There is no incremental path: the styling layer had to go in a single change.

That came to **804 `sx` props, 402 `Box` elements and 53 `Octicon` elements across 41 files**, now
**43 CSS module files**. Not one `sx` remains.

## What that changes for you

**Styles are a stylesheet again.** Until now the app generated its CSS in the browser at startup,
through styled-components. Primer 38 ships plain CSS, so the styling arrives as a file the browser
can cache and parse the way it parses any other — and the styled-components dependency is gone
entirely.

**Tooltips are reachable by keyboard.** Primer 38 refuses to attach a tooltip to something you cannot
focus, and it is right to: three badges here — the "analysed" marker, the rate-limit badge and the
per-depth Claude markers — had explanations that appeared on hover and were therefore invisible to
anyone not using a mouse. They are focusable controls now. This is the one behavioural fix in the
release and it was found by the upgrade rather than by us.

**Navigation icons stay at every window width.** Primer 38 hides them below 1440px by default, to
make room when a nav has many tabs. This one has five and they fit at any size this window can be;
losing the icons on a laptop would have been a regression dressed as a saving, so they are pinned on.

**A few components look slightly different**, because Primer restyled them: labels have an outline
they did not have, and some spacing shifted by a pixel or two. Nothing moved.

## Long-lived feature branches get a tab

Work on a branch shared between your fork and the upstream was invisible here. Both ends of its pull
requests live in the upstream, so the Pull requests tab's fork-head filter excluded them outright —
the branches this app was least able to show were the ones people spend weeks on.

The new tab tracks them and answers the question that actually comes up: *why is this sitting there.*
A pull request that is merely "open" tells you nothing; one that is open, green, mergeable and
**unarmed** tells you it is waiting for a person. So each pull request gets a stage strip — opened →
checks → mergeable → auto-merge armed → merged — with the reason it is stuck spelled out: *waiting on
required checks or a review*, *behind the base branch*, *conflicts — this one needs a working copy*.

**Each branch says how far behind the default branch it is** — `47 commits behind 2026.1`, in warning
colour, next to the fork standing. A branch can be in perfect sync with the upstream and still have
drifted months behind the branch it merges into, and of the two numbers only this one gets worse while
nobody touches anything. It is absent when the branch is level or ahead, because a label on every
healthy row is a label nobody reads.

It is **on by default**. Establishing that a repository has no shared branches under the prefix costs
two requests per poll — cheap enough that defaulting to off would mainly have meant the tab went
unfound by the people it was built for. Switch it off under **Settings → PR automation** and nothing
is polled or written for it.

### Three actions, and none of them merges

Bring the default branch into the feature branch; pull the upstream's copy of the branch down into
your fork; offer your fork's work back to the upstream's copy of the same branch. Nothing here targets
the default branch — getting a feature branch into `main` is somebody else's decision. Every action
opens a pull request and arms auto-merge, and GitHub does the merging when the required checks pass.
Landing directly in a feature branch is forbidden by branch protection, so a merge button here would
be a route around the rule that forbids it.

Bringing the default branch in goes through a **sync branch**: `sync/main-into-<branch>`, cut at the
default branch's current tip, with the pull request opened from there. The obvious alternative — a
pull request whose head *is* the default branch — can never finish, because `main` keeps moving, so
its diff changes under review and the head branch cannot be deleted when it merges. Pinned to one
commit, the pull request is a finite unit of work: it merges, it closes, and the next sync is a new
one. This deliberately mirrors the `create-merge.yml` workflow these repositories are already driven
by — the same branch name, the same `Merge branch 'x' into 'y'` title, the same merge commit rather
than a squash — because two tools producing differently-shaped pull requests for one operation leave
whoever reviews them guessing which one made this.

An existing sync branch is **reused, not moved**. Its pull request is almost certainly still open, and
that pull request is the unit of work — advancing the branch under a review would change what people
had already looked at. The consequence worth knowing: a sync branch left behind with no pull request
goes stale, and the next sync carries the older commit until it is deleted.

The row recommends what to do next. When a branch has fallen behind the default branch and no
backmerge is open, that becomes the recommendation and its button turns green — ranked below the fork
standing on purpose, because falling behind is a continuous chore wherever the default branch is busy,
and a recommendation that led with it would say the same thing on every row forever while burying the
work somebody actually wants to finish. It fills the silence rather than taking the front.

On the desktop, **Claude writes the offered pull request's title and description** from the commits
your fork has that the upstream's copy does not. You see and edit it before anything is published, and
a missing CLI or a slow reply falls back to a template rather than stopping the pull request. Issue
references and @mentions are stripped from whatever comes back: a hallucinated `Fixes #123` closes
somebody's issue the moment the pull request merges.

## The auto-rerun engine says what it decided

It used to work out a precise reason for every run it passed over and then throw it away. So a pull
request that had quietly stopped being retried looked exactly like one with nothing to do, and the
only way to tell them apart was to reason about the code. Three real bugs were hiding in that silence
and all three are fixed here.

Every decision is now recorded — **including the decisions not to act** — with the facts needed to act
on it: the age against the configured window for a run judged too old, the fingerprint and the streak
for a repeated failure, the record that settled it for one already handled. A verdict is written when
it *changes* rather than on every poll, so a size-capped log cannot fill with one repeated sentence.

Reading it needs no files: a **Diagnostics tab** (desktop, opt-in under **Settings → Diagnostics**)
shows the tail of the log inside the app, newest first, following live. Search covers each record's
attached details, so a run id, PR number or failure fingerprint finds its own lines even when the
sentence never mentions them.

Pull requests also gain an **arm auto-merge** button, an `auto-merge` badge naming the strategy and who
armed it — which is also how you tell which pull requests the engine will act on at all — and a
`re-run ×3` badge carrying every attempt, with the reason the engine has since gone idle if it has.

## Getting from a failing job to the failure

Every failing check and every failing job in a run has a button that opens that same failure in the
Failures tab. It was there before and it was **hidden unless the AI integration was on** — the
reasoning being that the only point of going was to have the failure explained.

That was wrong about the tab. The coloured log, the annotations and the copyable report are all there
without a model, and they are most of what it offers; the gate mainly meant that anyone using the app
in a browser had no way out of a job row at all. The button is now always present, with a bug icon
matching the tab it goes to.

The one condition that remains is the one that prevents a dead end: it appears only when the failure
is actually in that tab — **and that tab is stricter than it looks.** Only a flow's *latest* run is
considered, and only if it failed and finished within the last week. So a job in an older failing run
has no button, correctly: there is no row for it to land on.

That is defensible and it was also invisible. With debug logging on — `jobMonitorDebug.enable()` in
the console, or the Diagnostics tab in the desktop app — each flow now records why it contributed
nothing: *latest run is success, not a failure*, *no runs loaded yet*, *failed but outside the scan
window*, *failed but none of its jobs did*. The surprising one is the second state of the first: a
flow whose previous run failed contributes nothing the moment a newer run starts, because "in
progress" is not "failing". Verdicts are logged once and repeat only when they change. That list is bounded — a week's window, a bounded set of tracked pull
requests — so a job failing outside those bounds has no row to land on, and offering the trip anyway
would land you in a list that does not contain what you clicked.

## A flow reports its last result, not what it is doing now

A group in the Flows tab could read **pending** while everything in it had finished, and could show
fewer verdicts than it had flows.

Both came from treating a list of runs as one thing. The status was an aggregate over every run a
flow held, and that ranking puts failure first and unfinished ahead of finished — so a nightly still
going behind a push that had already passed dragged the whole flow to pending, and a flow that failed
five runs ago stayed red long after going green. Taking the newest run instead fixed that and broke
the other half: a flow mid-build had no result to report, so a group of three showed two verdicts and
the third read as missing.

Runs are independent attempts. The question worth answering is "how did this last come out", and only
a **finished** run answers it — so that is what a flow now reports, in every tab. The Overview had
always shown one run while the Flows tab aggregated; the rule is one function that all of them use.

Only *unfinished* runs are skipped, which matters: a flow that failed and is rebuilding still reads as
failed until the rebuild says otherwise, rather than going quiet for as long as CI is busy. That a run
is in flight is shown by a spinner beside the badge — a different fact, and kept.

Aggregation is still right where the parts really are parts of one whole: the check-runs of a commit.
That is unchanged.

## Where the new tab sits

The tab order is **Overview · Pull requests · Flows · Feature branches · Failures**. Feature branches
deals in pull requests and so belongs beside that tab by subject, but Flows is the everyday one of the
two, and the everyday tabs read better adjacent.

The README documents the tab properly, with screenshots: what each branch row is telling you, what the
three actions do, and why none of them merges anything.

## Under the hood

| | before | now |
|---|---|---|
| React | 18.3 | 19.2 |
| Primer | 36.27 | 38.35 |
| TypeScript | 6.0 | 7.0 |
| TanStack Table | 8.21 | 9.1 |
| styled-components | 5.3 | *removed* |
| Electron | 42.5 | 42.8 — **not** 43, see below |

**Electron stays on 42**, and that is a deliberate exception to this release's whole premise. Electron
43 was upgraded to and then reverted: Chromium 150 rewrote its StatusNotifierItem implementation, and
the result is that on Cinnamon the tray icon renders as the icon theme's missing-image placeholder and
**the tray menu does not open at all** — no Open, no Exit. That is not cosmetic; it is the loss of the
one interface a tray-resident app has when its window is hidden.

Measured rather than inferred, on the desktop where it showed up. Electron 42 registers its tray item
under a unique bus name with the menu at `/com/canonical/dbusmenu`; 43 registers a well-known name
`org.freedesktop.StatusNotifierItem-<pid>-1` with the menu at `/org/chromium/DbusMenu/1`. Both publish
the same icon the same way, so the icon file is not involved — running the *old* icon under 43
reproduces the placeholder exactly. Nothing reachable from the application changes it: passing a file
path instead of a `nativeImage`, and re-setting the icon after registration, were both tried.

The cost of staying is a quarter of Chromium security fixes, which is the wrong thing to give up and is
why this is written down rather than quietly pinned. Electron 42 still receives its own security
patches — 42.8.1 is one — so the range allows those and stops short of 43.

**TanStack Table 9** is a genuine rewrite rather than a rename: features are opt-in, the row model is
constructed rather than passed as a getter, and the cell accessor changed. The runs grid was migrated
to the real v9 API rather than to the compatibility entry point the package also ships, because a
compatibility shim is a decision to do the work later with less context.

That grid had **no test at all** — the kind of file where a table engine can be swapped underneath
and everything still typechecks while nothing renders, since column definitions are data and a table
configured with the wrong feature set builds a perfectly valid object that draws nothing. It has one
now, and it asserts output: rows arrive, in order, with the values the accessors were supposed to
reach.

**TypeScript 7** is the native compiler. It typechecks this project with no source changes.

## Notes for anyone building on this

- The CSS custom properties Primer 38 relies on come from **two** imports, not one: `primitives.css`
  defines sizes, radii and typography, while colours live only in the per-theme files. Importing the
  themes alone leaves every `--base-size-*` undefined, and the app renders in the right colours with
  no spacing at all — which looks like a layout bug rather than a missing import.
- A theme file is scoped to the exact `data-dark-theme` value it belongs to. This app uses
  `dark_dimmed`, so importing `dark.css` matches nothing and dark mode silently renders light.
- `style-src 'unsafe-inline'` remains in the Content-Security-Policy, but no longer for
  styled-components. What needs it now is the handful of `style` attributes carrying values that only
  exist at runtime — the width of a timeline bar as a percentage of a run's duration, a status colour
  looked up from a table. Those cannot become classes.
